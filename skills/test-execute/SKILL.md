# 执行会话

负责一个工单的阶段 5 中的合并前准备历史数据，以及阶段 6 执行、7 结果复核后的返工、8 登缺陷。只处理提示词里给的那一个工单目录，不碰其他工单。

页面由你自己用 ego-browser 操作，数据由你自己准备和核验，结果由你记录。用户只在复核时介入。

## 开场

1. 读 `.agent/workflow/状态规范.md`。
2. 读工单目录下的 `状态.md`。“会话”字段里没有 `执行=` 时，用 `get_session`（session_id 为 `self`）取当前会话 ID 补上；取不到就写 `执行=未知`。同时看 `get_session` 返回的模型和思考强度：本会话应使用 Sonnet 5.5（`claude-sonnet-5-5`）、思考强度 high。不一致时提醒用户在模型菜单里切换（会话不能改自己的模型），然后继续工作。
3. 系统为 QCAPP 时停止，告诉用户首版不支持 QCAPP 执行。
4. 按项目 `AGENTS.md` 的启动流程，加载该系统的知识 INDEX 和核心文档。
5. 读 `需求文档.md`、`需求理解.md`；工单目录里有技术方案等文档时一并读。
6. 读 `.agent/workflow/踩坑记录/执行.md`，避开已记录的坑。
7. 确定执行模式：
   - **用例模式**：`状态.md` 的测试粒度为“测试点+用例”，且 `测试用例/<uat|pre>-testcases.md` 存在。
   - **测试点模式**：其他情况，按 `测试点.md` 执行。
   - 测试粒度写的是“测试点+用例”但找不到用例文件时，停下告诉用户，不自行降级。
8. 有 `执行记录.md`、`回滚SQL.md`、`历史数据.md` 时一并读，了解前几轮的情况。
9. 按 `状态.md` 的阶段继续：阶段 5 且“历史数据”为“待准备”时，做“阶段 5：合并前准备历史数据”。等待为“Fenton”时，先把“下一步”的内容告诉用户，等用户回复。

每完成一个阶段或停下等用户时，都更新 `状态.md` 的阶段、等待、下一步、更新四个字段。

## 阶段 5：合并前准备历史数据

只在 `状态.md` 的“历史数据”为“待准备”时做。这时开发还没合并，UAT 上跑的是旧代码。历史数据必须在合并前准备好；合并后再造的数据不是历史数据，验证不了数据处理和兼容性。

1. 读 `历史数据.md`，逐项准备。
2. 先确认还没合并：页面已经出现本需求的新功能、新字段时，停下告诉用户，可能已经合并，不再准备。
3. 数据来源按优先级选：
   - 环境里现成的、满足“需要的数据”的旧数据，最接近真实的历史数据。
   - 用 ego-browser 在旧版页面上走业务流程产生的数据。
   - 页面造不出来时才用 SQL 插入或更新，并在该项注明“SQL 造数”，因为它不一定等于旧代码产生的数据，兼容性结论要打折扣。
4. 造数规则同阶段 6：先在 `回滚SQL.md` 写好造数 SQL 和回滚 SQL，不执行 DELETE，外部系统的数据先问用户。这些回滚 SQL 标为“历史数据”，现在不执行，合并后验证完再处理（见阶段 6 造数第 6 条）。
5. 每项填写：
   - 准备的数据：单号等标识，以及数据是怎么来的。
   - 合并前快照：用只读查询取出合并后要对比的关键字段，记下查询 SQL 和结果；页面表现要对比时，截图存到 `执行截图/合并前/`。
6. 全部准备好后，把“历史数据”改为“已准备”，等待改为“Fenton”，下一步写“企业微信通知开发合并 UAT，合并后把 ONES 需求流转为测试中”。向用户汇报准备了哪些数据，然后停下。执行轮次不变。
7. 某项准备不出来：在该项写明原因，告诉用户，由用户决定是否不等这一项就通知合并。

## 阶段 6：执行

### 准备

1. 执行轮次加一，写进 `状态.md`。
2. 环境默认 UAT。只有用户明确要求时才在 PRE 执行；不在 SIT 执行。用例模式下，PRE 需要 `pre-testcases.md`，没有就停下告诉用户，不回退 UAT。
3. 第 2 轮及以后：默认只重跑上一轮失败、阻塞的项，以及用户指出受影响的项；用户要求全量时才全量。
4. “历史数据”为“已准备”时，第 1 轮先验证 `历史数据.md` 里的各项，再做其他测试，避免其他测试改动这批数据：
   - 数据处理：用合并前快照的同一条查询再查一次，和快照、合并后预期对比。
   - 兼容性：用准备好的历史数据，在新代码上走关联测试点或用例的流程。
   - 结果照常记到关联的测试点或用例上，同时填进 `历史数据.md` 该项的“结果”。
   - 历史数据被别人改过或已经不存在时，该项记为阻塞，不要合并后重新造。
   - 全部验证完，把“历史数据”改为“已验证”。之后的轮次重跑历史数据相关项时，只能用原来那批数据。

### 造数

1. 按前置条件准备数据：结合知识库、数据库和需求文档，优先找现成数据，没有再造数。用例和需求文档里的订单号等只是占位说明，除非用户指定，不直接使用，按前置条件准备当前环境的真实数据。
2. 本系统的数据，可以直接插入或更新，不用逐条请用户确认；但执行前必须先在 `回滚SQL.md` 写好这条造数 SQL 和对应的回滚 SQL。
3. 外部系统控制的数据，不自己造，先停下问用户：是否由用户去外部系统操作。
4. 不执行任何 DELETE。
5. 数据准备不出来时，这一项记为阻塞，写明缺什么数据、查过哪里、为什么造不出，然后继续下一项。
6. 本轮结束后，不含 DELETE 的回滚 SQL 由你执行，并在 `回滚SQL.md` 标记已回滚。标为“历史数据”的回滚 SQL 是按旧结构写的，合并后可能已经不适用（字段被刷过、结构变了）：先按合并后的结构和数据重新核对，仍然适用且不含 DELETE 才执行，否则记入“待回滚清单”并写明原因。
7. 含 DELETE 的回滚 SQL 你不执行，先判断不回滚是否影响后续流程：
   - 会影响：立即停下请求用户处理。
   - 不影响：在 `回滚SQL.md` 的“待回滚清单”记下，写明判断理由，更新 `状态.md` 的“待回滚”条数，结束时统一交给用户。
8. 写库命令和连接方式遵循 `.agent/knowledge/数据库工作规范.md`；它的“写操作需确认”规则在执行会话里由本节造数规则代替。

### 页面操作

1. 用 ego-browser 操作页面。为完成测试步骤需要点的业务按钮可以直接点，但只在当前执行环境里操作。
2. 关键结果截图存到工单目录的 `执行截图/第<轮次>轮/`，文件名带用例标题简称或测试点编号。
3. 页面结果需要数据库佐证时，用只读查询核验；不需要核验时不查。
4. 登录失效、没有权限、环境不通等情况，记为阻塞，不猜测、不绕过。

### 用例模式：记录到执行结果文件

结果用 testcase-assistant skill 目录下的 `scripts/result.mjs` 维护（项目里装在 `.claude/skills/testcase-assistant/`），用法先看 `node <脚本> -h`。结果文件是 `测试用例/execute-testcase/<uat|pre>-execution-result.json`，按 `case_id`、`step_id` 关联用例，不要手写或直接改这个 JSON。

1. 用 `status` 查看用例清单和执行进度，不通读整个用例文件。
2. 逐条执行：用 `show --case <标题>` 读取一条用例，后续命令的 `--case` 用 `show` 输出的完整标题。
3. 按前置条件造数，然后按步骤操作页面、核验结果。
4. 每做完一步就用 `record` 写入，不要攒到最后：

   ```bash
   node "<testcase-assistant目录>/scripts/result.mjs" record "<用例.md>" \
     --case "<完整用例标题>" --step 2 --result FAILED \
     --actual "第1轮：提交后列表仍显示旧状态“待审核”；数据 SP2026100071；截图 执行截图/第1轮/补单提交_02.png"
   ```

5. `--result` 取 `PASSED`、`FAILED`、`BLOCKED`。
6. `--actual` 以“第N轮：”开头，写看到的实际表现、用了哪些数据、证据（截图相对路径、核验 SQL 的结论）。这是你执行所得，不写“用户已验证”；只有用户亲自验证过的步骤，才按项目规范注明“用户已验证”。
7. 前置数据阻塞的用例，用 `--step all --result BLOCKED` 记录，`--actual` 写阻塞原因。
8. 本轮的卡点和疑似缺陷写进 `执行记录.md` 的“第N轮”小节（格式见下方“本轮小结”）。

### 测试点模式：记录到 测试点.md

`测试点.md` 本身就是执行记录，不另建文件。它由理解设计会话按下面的格式写好，你只填结果相关的列和章节：

```markdown
## 入库单补单

| 编号 | 测试点 | 结果 | 实际表现 | 证据 |
|---|---|---|---|---|
| 1 | 补单时仓库下拉只显示该国别的仓库 | 通过 | 第1轮：美国单只显示 3 个美国仓；数据 RK2026110012 | 执行截图/第1轮/1.png |
```

1. 每做完一个测试点就填写该行，不要攒到最后。
2. 结果填“通过 / 失败 / 阻塞”；实际表现以“第N轮：”开头，写看到了什么、用了哪些数据；证据写截图相对路径或核验 SQL 的结论。
3. 结果列只保留最新一轮；重跑时整格覆盖。
4. 表格缺结果列，或测试点格式不同时，补齐“结果 / 实际表现 / 证据”三列，不改编号和测试点内容。
5. 本轮的卡点和疑似缺陷写在 `测试点.md` 末尾的“执行情况”一节，每轮一个小节（格式见下方“本轮小结”）。

### 本轮小结

用例模式写在 `执行记录.md`，测试点模式写在 `测试点.md` 末尾的“执行情况”。每轮一个小节：

```markdown
### 第N轮（UAT，2026-11-16）

通过 x / 失败 y / 阻塞 z

**卡点**

1. 原因、查过哪里、需要用户做什么

**疑似缺陷**

1. 现象、复现步骤、预期、实际、证据；判断依据（需求明确 / 按历史逻辑推断）
```

### 本轮结束

1. 按造数规则处理回滚。
2. 把阶段改为“7 结果复核”、等待“Fenton”，下一步写清去哪个文件复核第 N 轮的卡点和疑似缺陷。
3. 向用户简要汇报：通过、失败、阻塞各几项，卡点和疑似缺陷列表，待回滚条数。然后停下。

## 阶段 7：结果复核（用户主导）

1. 用户分析卡点、判断疑似缺陷时，回答要说清依据和证据。
2. 用户补充的业务知识，按项目 `AGENTS.md` 的知识管理规则写进知识库。
3. 用户要求修改用例时，按 testcase-generator 的规则改 Markdown：保留已有 `case_id`、`step_id`，新增步骤生成新 UUID。已记录步骤的预期被修改时，下一轮重新 `record`；删除用例或步骤后，用 `status --prune` 清理失效结果。
4. 用户解决卡点后要求再跑：阶段改回“6 执行”、等待“执行会话”，开始下一轮。
5. 用户确认有缺陷：阶段改为“8 登缺陷”、等待“执行会话”，进入阶段 8。
6. 用户确认没有缺陷：进入“结束”。

## 阶段 8：登缺陷

1. 先看 `状态.md` 的“缺陷”字段，已登记过的不重复写。
2. 把用户确认的缺陷写进 `缺陷草稿.md`，每个缺陷包含：标题、所在页面、前置条件、复现步骤、预期结果、实际结果、截图路径、环境。
3. 等待改为“Fenton”，请用户确认草稿。
4. 用户确认后，在 ONES 创建缺陷：首版由用户在 ones-page 页面上按草稿创建，创建后把缺陷编号告诉你。
5. 把缺陷编号写进 `状态.md` 的“缺陷”字段，然后进入“结束”。

## 结束

1. 阶段改为“结束”、等待“无”。
2. 向用户汇报收尾事项：待回滚清单（如有）需要用户回滚；ONES 需求流转为“测试通过”、测试任务改为“已完成”由用户操作。

## 边界

1. 不执行任何 DELETE，也不执行含 DELETE 的回滚。
2. 不在 ONES 里做任何写操作。
3. 不删除文件。
4. 不改 `需求理解.md`；`测试点.md` 只填结果相关的列和“执行情况”一节，不改测试点本身；`历史数据.md` 只填“准备的数据”“合并前快照”“结果”；用例只在用户要求时修改。发现它们有问题时记进疑问，告诉用户。

## 踩坑记录

1. 遇到工作流本身的问题（规则、交接、会话安排、工具用法），并且换一个需求还会再遇到时，按 `状态规范.md` 的“踩坑记录”一节写进对应文件，通常是 `.agent/workflow/踩坑记录/执行.md`。
2. 测某个需求时在具体页面、字段、数据上踩的坑，不写进踩坑记录。
3. 新增或补充了条目，要在汇报里告诉用户。
