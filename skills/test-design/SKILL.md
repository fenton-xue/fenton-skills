# 理解设计会话

负责一个工单的阶段 1 接单（下载需求）、2 需求理解、4 测试设计。只处理提示词里给的那一个工单目录，不碰其他工单。

## 开场

1. 读 `.agent/workflow/状态规范.md`。
2. 读工单目录下的 `状态.md`。“会话”字段里没有 `理解设计=` 时，用 `get_session`（session_id 为 `self`）取当前会话 ID 补上；取不到就写 `理解设计=未知`。同时看 `get_session` 返回的模型和思考强度：本会话应使用 Opus 5.5（`claude-opus-5-5`）、思考强度 high。不一致时提醒用户在模型菜单里切换（会话不能改自己的模型），然后继续工作。
3. 按项目 `AGENTS.md` 的启动流程，加载该系统的知识 INDEX 和核心文档。
4. 读 `.agent/knowledge/Other/ONES需求测试流转.md`，了解需求状态、合并 UAT 的时机和历史数据的两种情形。
5. 读 `.agent/workflow/踩坑记录/设计.md`，避开已记录的坑。
6. 按 `状态.md` 的阶段继续：阶段 1 从“下载需求”开始，阶段 2 从“需求理解”开始，阶段 4 从“测试设计”开始。等待为“Fenton”时，先把“下一步”的内容告诉用户，等用户回复。

每完成一个阶段或停下等用户时，都更新 `状态.md` 的阶段、等待、下一步、更新四个字段。

## 阶段 1：下载需求

1. 用 ego-browser 打开 `状态.md` 里的需求链接，只读页面，不点任何会改数据的按钮。
2. 需求内容有两种形式，都要识别：
   - 写在需求描述里。
   - 需求关联了一篇 Wiki，正文在 Wiki 里。两种同时存在时都要。
3. Wiki 也用 ego-browser 打开读取。
4. 加删除线的内容是已失效的旧需求，保存前去掉。从 DOM 取正文时，去掉 `<s>`、`<del>`、`<strike>` 以及样式含 `line-through` 的元素。
5. 图片下载到工单目录的 `images/`，正文用相对路径 `images/xxx.png` 引用。下载失败的保留原链接，并在 `需求理解.md` 的疑问里注明。
6. 保存为 `需求文档.md`：开头写来源链接和下载日期，正文尽量保留表格、列表结构。描述和 Wiki 都有时分两节。
7. 已有 `需求文档.md` 时不覆盖，另存为 `需求文档-<日期>.md`，并告诉用户有新旧两版。
8. 完成后把阶段改为“2 需求理解”、等待“设计会话”，直接进入阶段 2。

## 阶段 2：需求理解

1. 读 `需求文档.md`；工单目录里有技术方案等文档时一并读。
2. 按项目 `.agent/code/源码定位规范.md` 查源码，弄清相关的历史逻辑和本次改动。数据库只做只读查询，遵循 `.agent/knowledge/数据库工作规范.md`。
3. 写 `需求理解.md`：
   - 需求要点：用自己的话复述，每条一行。
   - 影响范围：涉及的页面、接口、表、上下游系统。
   - 每条结论标明出处：需求明确 / 源码确认 / 按历史逻辑推断。开发还没完成时，后两者要特别标出，这是用户需要判断方向的地方。
   - 历史数据：需求或技术方案提到刷数、存量数据处理，或改动会影响旧数据的读取和使用时，单独列出。这类测试要在开发合并代码之前准备数据，见阶段 4。合并 UAT 由 Fenton 通知开发后才会发生，不会突然合并；准备时机由调度员按排期安排，你只负责列出需要哪些历史数据，不要建议何时准备或催促尽早准备。
   - 疑问清单：编号列出，同时写进 `状态.md` 的“疑问”。
4. 写完后等待改为“Fenton”，下一步写“读需求理解.md，在理解设计会话里和 agent 对齐理解”，然后向用户简要汇报要点和疑问，停下。

### 关口 A：对齐理解

1. 用户会自己读需求，并问你问题。回答时说清依据和出处，不确定就说不确定。
2. 用户补充的业务知识，按项目 `AGENTS.md` 的知识管理规则写进知识库；只和本工单相关的写进 `需求理解.md`。
3. 用户答复的疑问，在 `需求理解.md` 和 `状态.md` 里标为已答复，写上答复内容。
4. 用户确认理解一致后，问用户测试粒度：只列测试点，还是测试点+用例，写进 `状态.md`。
5. 把阶段改为“3 估时排期”、等待“Fenton”，下一步写“在 ONES 建测试任务并排期，完成后告诉理解设计会话，或把阶段改为 4、等待改为设计会话”。

## 阶段 3：估时排期

由用户在 ONES 完成。用户告诉你已完成时，把阶段改为“4 测试设计”、等待“设计会话”，进入阶段 4。

## 阶段 4：测试设计

1. 写 `测试点.md`：按功能或场景用二级标题分组，每组一张表，每条测试点一行，写清要验证什么，不写操作步骤。编号全文连续（1、2、3…）。没有用例时，执行会话会直接在这张表里填结果，所以“结果 / 实际表现 / 证据”三列先建好、留空：

   ```markdown
   ## 入库单补单

   | 编号 | 测试点 | 结果 | 实际表现 | 证据 |
   |---|---|---|---|---|
   | 1 | 补单时仓库下拉只显示该国别的仓库 | | | |
   ```

2. 测试粒度为“测试点+用例”时，使用 testcase-generator skill，在 `测试用例/` 下生成用例。
3. 有测试点或用例依赖合并前就存在的历史数据时，写 `历史数据.md`，每项一节（执行会话会在合并前填“准备的数据”和“合并前快照”，合并后填“结果”）：

   ```markdown
   ## H1 已收货入库单的仓库字段被刷为默认仓

   - 关联：测试点 3、5（有用例时写用例标题）
   - 情形：数据处理 / 兼容性
   - 需要的数据：合并前就存在、仓库为空的已收货入库单
   - 合并后预期：仓库字段被刷为该国别默认仓（依据：技术方案“存量数据处理”）
   - 准备的数据：
   - 合并前快照：
   - 结果：
   ```

   - 情形分两种：“数据处理”指开发合并时会处理测试环境的存量数据，合并后验证数据被处理成预期的样子；“兼容性”指合并后验证新代码能否正常处理旧代码产生的数据。
   - 测试点和用例里照常写验证内容；用例的前置条件只写数据状态（如“合并前已存在的已收货入库单”），不写造数手段。
4. 写完后等待改为“Fenton”，下一步写“review 测试点.md（和测试用例、历史数据.md）”，向用户汇报后停下。
5. 用户提出修改就改，改完再请用户 review。
6. 用户 review 通过后，把阶段改为“5 等介入”、等待“调度会话”；`状态.md` 的“历史数据”有 `历史数据.md` 时写“待准备”，没有写“无”；下一步写“等需求提交测试且一轮测试排期到达”。本会话的工作到此结束。

## 边界

1. 不执行任何写库 SQL，不在 ego 里点会改数据的按钮。
2. 不在 ONES 里做任何写操作。
3. 不删除文件；需要替换的文件另存新版本。
4. 不进入阶段 5 以后的工作。

## 踩坑记录

1. 遇到工作流本身的问题（规则、交接、会话安排、工具用法），并且换一个需求还会再遇到时，按 `状态规范.md` 的“踩坑记录”一节写进对应文件，通常是 `.agent/workflow/踩坑记录/设计.md`。
2. 测某个需求时在具体页面、字段、数据上踩的坑，不写进踩坑记录。
3. 新增或补充了条目，要在汇报里告诉用户。
