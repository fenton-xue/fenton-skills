# 黑盒功能测试用例生成器

只设计功能测试（黑盒），不涉及接口、性能、安全和自动化测试。交付物是测试用例 Markdown；执行结果与截图由下游 testcase-executor 维护。

## 输出目录

测试用例固定存放在需求目录下：

```text
<需求目录>/测试用例/
├── uat-testcases.md
├── pre-testcases.md
└── execute-testcase/
    ├── uat-execution-result.json
    ├── pre-execution-result.json
    ├── uat-screenshots/
    └── pre-screenshots/
```

默认只生成和维护 `uat-testcases.md`。仅当用户明确要求 PRE 版本时生成 `pre-testcases.md`。`execute-testcase/` 下的文件和截图不属于本 Skill 的交付物。

## Markdown 格式

创建或更新用例前，读取 [references/uat-testcases.example.md](references/uat-testcases.example.md) 了解完整 Markdown 结构、多级模块、多个步骤、分点前置条件和多行内容。格式约束：

- frontmatter 必须包含 `environment`、`title`、`created_at`；`environment` 只能是 `UAT` 或 `PRE`，`title` 非空，`created_at` 是有效时间。
- 创建文件时写入 `created_at`；更新已有文件时保留原值。
- 一级标题固定为 `测试用例`，每条用例使用二级标题，报告内用例名称唯一；名称允许在后续更新中修改。
- 每条用例的二级标题后必须且只能包含一个 `**case_id:** <UUID>`，UUID 格式合法且在报告内唯一。
- `module_path` 使用 Markdown 无序列表，至少包含一项。
- 每条用例包含 `### 前置条件`；无特殊前置条件时内容写 `-`。
- 步骤使用 `### 步骤 N`，从 1 开始连续编号；标题后必须且只能包含一个 `**step_id:** <UUID>`，UUID 格式合法且在报告内唯一；每一步均包含 `action` 和 `expected`。
- 空内容统一写 `-`。
- 更新既有用例时优先通过 `case_id` 定位；用例名称和 `module_path` 是可修改属性，不作为实体身份。

执行结果文件由下游 testcase-executor 的脚本创建和维护。不要在测试用例 Markdown 中写入执行状态、页面名称、页面 URL、实际结果或截图，也不要由本 Skill 创建执行结果文件。

## 生成范围

1. 根据用户确认的范围设计用例，并结合整个需求文档理解业务意图。
2. 用户明确指定一个小标题时，只生成或更新该小标题对应的用例。
3. 用户未指定小标题时，停止生成并询问是否需要覆盖整篇文档。
4. 用户确认覆盖整篇文档后，一次性生成全部小标题的用例并交付 Review。
5. 用户不需要覆盖整篇文档时，等待用户指定小标题。

## 模块与用例命名

1. 阅读全文后整体规划 `module_path`，层级数量按业务结构动态确定。
2. 模块名称可按业务语义优化，不必机械复用需求标题。
3. 每条用例必须写出完整 `module_path`。
4. 用例名称使用 `{需求号}-{两位编号}-{测试点描述}`，例如 `#84313-07-登录按钮验证`。
5. 需求号从需求文档文件名提取。
6. 编号从 `01` 开始，并在跨最小级模块时重置。最小级模块是 `module_path` 的最后一项。
7. frontmatter 的 `title` 使用包含需求号的完整需求名称，例如 `#84313 登录能力优化`。

## 稳定 ID

1. 新建用例时生成新的 UUID 作为 `case_id`；新建步骤时生成新的 UUID 作为 `step_id`。
2. 修改用例名称、`module_path`、前置条件、`action`、`expected` 或步骤顺序时，保留对应实体原有 UUID。
3. 插入步骤只为新步骤生成 `step_id`；保留其他步骤的 `step_id`，再按当前顺序重新连续编号标题。
4. 删除后重新创建的用例或步骤视为新实体，必须生成新的 UUID，不复用已删除实体的 ID。
5. 更新已有文件时先解析当前报告，通过 `case_id` 找到目标用例，并通过 `step_id` 识别已有步骤；不得根据名称、模块或步骤序号重新分配 UUID。
6. `case_id` 和 `step_id` 只用于 Markdown 与执行结果的稳定关联，不写入 XMind 转换结果。

需要生成新 UUID 时，使用 Node.js 内置的 `crypto.randomUUID()`：

```bash
node -e "console.log(require('node:crypto').randomUUID())"
```

该命令每次生成一个 UUID；每个新用例和新步骤分别执行一次，不复用输出。

## 步骤设计

1. 账号权限、页面位置或数据状态只有符合“前置条件”章节的保留标准时才写入前置条件；`action` 从当前测试点所需的最小有效操作开始，只保留选择条件、输入数据、点击、勾选、粘贴、提交、保存、查询或审核等实际操作。仅当登录、导航或切换页面本身是当前测试点时，才在 `action` 中描述这些操作。
2. 将规则、展示逻辑、字段说明和限制条件转换为可执行操作，禁止直接复述需求。
3. 相近操作聚合在同一用例中，使用多个步骤覆盖并列场景，避免拆成大量单步骤用例。
4. 并列步骤之间没有逻辑依赖时，在 `action` 开头使用括号标明当前场景。
5. 每个步骤同时包含一个 `action` 和一个 `expected`，两者严格一一对应。
6. 一个步骤只验证一个明确测试点；不同测试点拆成不同步骤。
7. 步骤从 `1` 开始连续递增。
8. 覆盖需求支持的主要操作路径，例如手动输入、批量粘贴、弹窗选择和列表勾选。
9. 分支、权限、范围和优先级必须设计明确测试点；优先项与兜底项分别验证。
10. 输入类操作在 `action` 中写出具体、中性的测试数据。禁止单独增加测试数据字段。

## 复杂内容分点

1. 前置条件包含两个及以上相互独立的必要条件时，无论句子长短，必须使用分点和换行；只有一个条件时使用连续文本。
2. `action`、`expected` 包含多个连续子操作或多个相关展示点，单段表述不易快速理解时，使用分点和换行提高可读性；多个独立测试点仍拆成不同步骤，不使用分点替代步骤拆分。
3. 准备使用分号连接多项内容时，必须先判断各项是否为相互独立的条件或信息；相互独立时改用分点，同一条件内部的补充说明才保留为连续文本。
4. 分点使用从 `1. ` 开始连续编号的原生 Markdown 有序列表，每项单独一行。
5. 同一字段中的分点从 `1. ` 开始连续编号，不在编号项前后混入未编号文本。

## 预期结果

1. `expected` 必须明确、确定、可观察，只描述一种系统表现。
2. 禁止使用“若”“如果”“取决于”“视情况”等假设性或条件性表述。
3. 预期结果只写系统实际表现，不写测试意图、原因解释或操作说明。
4. 条件分支拆成独立步骤，每个步骤只描述一种确定状态。

## 前置条件

1. 每条用例必须包含 `### 前置条件` 区块。
2. 前置条件不是通用执行环境清单。只写测试人员需要在执行前刻意准备或确认，并且会直接决定当前用例操作路径或预期结果的状态。
3. 保留以下内容：特殊账号、角色或权限；指定业务数据及其状态；会决定展示、权限或流程分支的配置；必须提前完成的历史操作或持久化状态；多账号、多设备场景中需要刻意制造的状态差异。
4. 省略以下内容：已登录、App 可用、系统可访问等通用条件；可由操作自然表达的通用数据准备；未编辑、未选择、未保存过等默认状态；已由当前用例前面步骤建立的状态；可从用例名称、`module_path` 或操作中明确推断的信息。
5. 默认状态只在用例专门比较默认与非默认状态，或必须控制历史残留数据时写入前置条件。
6. 判定时先尝试删除该条件：在通常的默认测试上下文中，操作仍可执行且预期结果仍明确时，应省略该条件。
7. 测试环境由 frontmatter 的 `environment` 定义。除非环境差异本身是当前测试点，否则禁止在前置条件或 `action` 中重复“登录UAT/PRE”“进入UAT/PRE页面”“XX系统测试环境可用”等通用环境说明。
8. 无特殊前置条件时使用 `-`。
9. 禁止单独增加优先级字段。

## 校验与 XMind 转换

每次生成一批新用例后，对更新后的完整 Markdown 运行一次校验。Review 期间只修改已有用例时不运行校验；Review 中新增用例时，新增完成后运行一次：

```bash
node "<testcase-generator目录>/scripts/testcase-markdown-utils.mjs" "<需求目录>/测试用例/<uat|pre>-testcases.md"
```

转换为可导入 XMind 的 Markdown：

```bash
node "<testcase-generator目录>/scripts/create-xmind-markdown.mjs" "<需求目录>/测试用例/<uat|pre>-testcases.md" [输出文件.md]
```

未指定输出路径时，默认生成 `<uat|pre>-testcases.xmind.md`。转换结果保留需求标题、模块层级、`cs` 用例标记、`pc` 前置条件标记、`tpP2` 优先级标记，以及操作与预期的父子层级；不包含 `case_id` 或 `step_id`。

## PRE 复制流程

1. 仅当用户明确要求生成 PRE 版本时，复制 `uat-testcases.md` 为 `pre-testcases.md`。
2. 将 frontmatter 的 `environment` 改为 `PRE`。
3. 根据 PRE 环境调整相关测试数据。
4. 保留全部 `case_id` 和 `step_id`，并保留模块、用例名称、步骤编号、操作结构和步骤数量。

## 工作流程

1. 阅读完整需求文档并确认生成范围。
2. 定位 `<需求目录>/测试用例/uat-testcases.md`。
3. 读取已有 Markdown；不存在时创建 UAT 文件。
4. 规划模块结构和测试点；更新已有报告时先按 `case_id` 建立用例索引，并按 `step_id` 建立步骤索引。
5. 生成或更新测试用例；只为新实体生成 UUID，保留所有既有实体的 UUID。
6. 本批生成了新用例时，使用校验脚本对完整 Markdown 检查一次格式、用例名称唯一性、UUID 格式与唯一性和步骤连续性；仅根据 Review 修改已有用例时跳过校验。
7. 提供用例数量、变更摘要及 Markdown 文件链接。
8. 暂停等待用户 Review。
9. 根据 Review 更新同一 Markdown；仅修改已有用例时不运行校验，新增用例时在新增完成后运行一次。
10. 指定小标题模式下，等待用户说“下一个”后再处理下一批。

指定小标题模式一次只处理一个阶段；整篇文档模式必须先获得用户确认。默认流程只创建或更新 UAT Markdown，不创建 PRE 文件或任何执行结果。
